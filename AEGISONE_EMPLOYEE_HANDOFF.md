# AegisOne Employee Dashboard — Developer Handoff Document

This document serves as a comprehensive technical handoff for the **AegisOne Employee Dashboard**. It details the frontend architecture, backend endpoints, database schema, and security workflows currently implemented. 

This information is specifically formatted to help the co-developer understand the telemetry generated by employees and the specific UI structures implemented so they can build the **Supervisor (Lead)** and **Super Admin** dashboards on top of this exact aesthetic and data model.

---

## 1. Role & Access Hierarchy

The platform relies on a 4-tier Role-Based Access Control (RBAC) system defined in `api/auth/roles.py`:

1. **`employee`**: Can only view their own personal telemetry, scan history, and extension status.
2. **`department_admin` (Lead)**: Can view aggregate analytics and telemetry for users within their specific `department` or assigned group.
3. **`super_admin`**: Can view telemetry for the entire `organization_id`, manage users, and enforce global policies.
4. **`global_admin`**: Platform owner; can manage multiple organizations and view cross-tenant system metrics.

## 3. Core Database Architecture (PostgreSQL / SQLAlchemy)

The telemetry generated by the Employee Extension is stored in these critical tables (`api/database/models.py`). To build the Admin dashboard, you will primarily run `GROUP BY` and `COUNT()` queries against these tables, filtering by `organization_id` or `department`.

### A. Core Identity & Devices
*   **`users`**: 
    *   `id`, `email`, `password_hash`, `full_name`, `role` (String), `organization_id`, `department`, `is_active`.
*   **`devices`**:
    *   `device_id` (Primary Key, linked to extension install), `user_id`, `platform`, `browser`, `extension_version`, `last_heartbeat`.

### B. The Threat Telemetry Tables (CRITICAL FOR ADMIN)
*   **`website_scans`**: Every URL visited/scanned.
    *   `scan_id`, `user_id`, `url`, `domain` (for grouping), `scan_type` (url, text, image, attachment, website), `risk_score` (0-100), `decision` (allow, warn, block), `threat_type` (e.g., phishing, malware), `top_factors` (JSON), `created_at`.
*   **`download_events`**: Every file downloaded by the browser.
    *   `id`, `user_id`, `file_name`, `file_hash` (SHA-256 for IOC tracking), `mime_type`, `risk_score`, `decision`, `block_reason`, `timestamp`.
*   **`credential_events`**: Phishing credential interception.
    *   `id`, `user_id`, `target_url`, `username`, `password_hash` (partial/masked), `decision`, `intercepted_at`.

### C. System Tables
*   **`policies`**: Admin-defined rules (`policy_id`, `organization_id`, `config` JSON). Employee extensions fetch these via `/policy/current`.
*   **`security_events`**: Generic system events (e.g., Extension Disabled, Privacy Mode toggled).

## 4. Backend API Endpoints (FastAPI)

We implemented a suite of endpoints in `api/routers/compatibility.py` to power the Employee dashboard. 

**How the Employee gets data:**
*   `GET /user/xai`: Returns deep XAI explanation JSONs (Confidence, Target, Reasons, Remediation).
*   `GET /user/analytics`: Returns data formatted specifically for Recharts (`dailyTrend` arrays, `threatTypes`, `riskDistribution`).
*   `GET /user/threats`: Aggregates the raw `website_scans` into distinct threat vectors (`recent` list and grouped `cards`).

**What the Admin Developer needs to do:**
You will need to create a new file: `api/routers/admin.py`.
Instead of filtering by `user_id` or `email`, your SQLAlchemy queries will look like this:

```python
# Example Admin Query for Department Leads
q = await db.execute(
    select(func.count(WebsiteScan.id))
    .join(User, WebsiteScan.user_id == User.id)
    .where(User.department == current_admin.department, WebsiteScan.decision == "block")
)
```
